# 随手件：不完整流恢复注入（projection-only 续作指令）

> 来源：grok-build-proxy v1.0.42 已发版（PATCHES 二十一期，随手件-P3；
> 语义源 Step-Code `step-stream-recovery.ts`）。≤1 人天。

## 1. 问题

国产网关/聚合器的流中断是高频现实：响应流中途断开（`stream ended before/without`
族错误），已产生的部分回复与工具调用被丢弃。pigo 现有机制：

- 传输层连接期重试只覆盖 429/503/529 且**绝不重放已消费流**
  （`internal/provider/transport`，harness 矩阵 US-006）；
- 工具失败有分类重试（`isRetryableToolError`）；
- 流中断后模型不知道"上次为什么断、哪些工作仍有效"，往往重发大 payload
  再次中断，形成断流循环。

## 2. 语义（Step-Code 定稿，已验证）

检测到可重试的流中断错误后，**下一轮请求**注入一条恢复提示（三要点）：

1. 上一次响应中断，其中的工具调用未执行；
2. 先前工具结果确认过的工作仍然有效（不必重做）;
3. 行为指令：改用更小响应（约 50 行/几 KB）、大文件用 write/edit 分块增量
   构建、勿整文件重发大 payload。

**projection-only**：注入物不落会话文件、不是合成用户消息——只在构建下一轮
请求的消息投影时拼入，重放/分支导航不会继承陈旧恢复态（状态每轮从会话现算，
不存内存标记）。

## 3. 落点（pigo 侧）

- **判别式**：`internal/provider/transport` 流式失败分类中新增"流中断"判别
  （区别于连接期失败——前者已有部分响应被消费）；具体落点施工时对照
  流式失败模型（dual failure model：构建失败走 error、运行期失败走流内
  terminal event）核实，改判别不改重试策略。
- **注入点**：`internal/runtime/loop.go` 内层循环的下一轮消息构建处——
  上一轮以流中断错误结束时，给本轮请求的消息列表尾部拼一条 system 角色
  恢复提示（projection-only，不进 `MessageList`、不进会话文件）。
- **边界**：不拥有 retry（传输层重试照旧）；与 doom-loop 防护正交——
  恢复提示只在检测到中断的下一轮注入一次，连续中断按现有重试/停止语义走。

## 4. 验收标准

1. 流中断后下一轮请求含恢复提示（faux provider 断言注入内容与三要点齐备）。
2. 注入不落会话文件（session JSONL 无该条目断言）、resume 后不复活。
3. 连续中断不叠加多条提示。
4. 正常完成/其他错误类型不注入（零误伤）。

## 5. 规模

C 级粗估：≤1 人天（判别式核实占一半）。
