# 缺陷侦探 — 三轴深度审查工作流

对当前仓库执行一次以「可验证缺陷」为目标的深度审查。产出不是架构感想，
而是每条都有 file:line 证据、按 P0/P1/P2 分级的行动清单。

## 铁律（优先级高于一切）

1. 每条结论必须附 `file:line` 证据，禁止无出处指控
2. 「怀疑」必须先 grep / 读码取证后才允许写入报告
3. 默认文档在撒谎：README 声称的每个特性都要端到端追踪到真实调用点
4. 先做领域威胁建模再动手：先回答"这类项目的致命弱点通常是什么"，带着答案去审

## 阶段 0：检索加速 + 骨架扫描

**核心原则：先用廉价检索缩小靶区，再花 token 精读。禁止一上来逐文件全文通读。**

按性价比从高到低使用检索手段：

- **符号/调用关系查询**：优先用语义代码导航（LSP：找定义/找引用/调用层级），
  一次拿到"符号定义 + 类型 + 调用路径"，替代多轮 grep→read 往返。适合回答
  "这个流程涉及哪些代码"
- **精准 grep 取证**：验证死代码、未接线的 flag、错误吞噬点时直接 grep
  函数名/字段名（如 `grep -rn "funcName" --include="*.go" .`），
  一条命令完成取证，不靠通读碰运气
- **批量并行读取**：确定要读的文件一次性并行读入，不要串行往返
- **广度扫描委派**："在哪/有没有"类大范围问题派给搜索/探索类子代理，
  只要结论不要文件转储；主上下文只保留核心链路源码

骨架扫描（本阶段唯一允许的全局动作）：
- 文件清单 + 各文件行数分布，定位核心包与异常大的文件
- 抄录 README/docs 声称的全部功能 → 形成「承诺清单」（供阶段 2C 核对）
- 工程配置盘点：CI workflow 数量与触发条件（push/PR/tag）、有无 lint 配置、
  测试规模、依赖健康度

## 阶段 1：主链路精读（只读核心，其余按需）

按「入口 → 核心抽象 → 资源生命周期」亲自通读核心链路源码（通常 ≤15 个文件，
行数分布异常大的文件优先）。每个文件带四个问题读：
- 共享状态有哪些？每次读写是否都在同一把锁的保护下？
- 定时器回调 / 后台任务里跑了什么？会不会泄漏？
- 错误去了哪里：吞掉、降级、还是上报？
- 失败路径上状态清理完整吗（断连后哪些字段成了脏数据）？

## 阶段 2：三轴深查

### A. 设计轴
- 领域威胁模型 top3 是否被防御；可靠性机制是否闭环（断连/超时/崩溃/重试各有归宿）
- 默认值是 fail-open 还是 fail-closed（例：白名单为空 = 全放行？）
- 面向 LLM/Agent 的接口：错误语义是否结构化，能否支撑调用方安全重试

### B. 实现轴（bug 密度最高）
- 并发审计：列出跨 goroutine/线程 共享的结构体字段，逐一核对读写是否都在
  同一把锁下；重点查定时器回调、check-then-act 的 TOCTOU、channel 收发配对
- 错误吞噬：grep `_ =`、空分支、静默 fallback（解析失败回退默认值之类）
- 语义偏差：上限是单流还是合计？单位 ms 还是 s？声称的幂等真成立吗？
- 字符串 footgun：环境变量展开（os.Expand 会吃掉字面 `$`）、模板替换顺序、
  shell 引号拼接

### C. 工程轴
- 拿「承诺清单」逐条 grep 实现 + 调用点，抓两类问题：
  「已文档化但未实现」「有 flag 但无人消费」
- 看到逻辑被内联重复时，立刻 grep 原函数名确认是否死代码
- 本机跑不了的检查（race detector / sanitizer / 其他平台）CI 有没有补位？
- 测试质量：测的是纯函数还是最易错的状态机与并发路径？集成测试如何隔离？

### 范围边界

与 `review-it` 的划界：review-it 是改动收口前的**例行评审**（本次 diff 是否
达标），本 skill 是对整个仓库的**深度审计**（存量缺陷挖掘），两者不互替。
纯可维护性/结构简化类问题只在影响正确性/缺陷时纳入（异常大文件按阶段 1
规则优先精读）。

## 阶段 3：运行验证

能跑的全跑：build、vet、test、`-race`（注意平台限制）、lint。
跑不了的明确记录原因，「本机缺口 × CI 缺口」本身作为工程 finding 写进报告。

## 阶段 4：输出报告

1. 第一句话给总评（TLDR），不要铺垫
2. 按「做得好的 / 问题」组织；问题分 设计/实现/工程 三组
3. 每条 finding：`file:line` + 触发条件 + 影响 + 具体修法
4. 结尾给 P0/P1/P2 行动清单（P0 = 正确性与安全）
5. 「做得好的」要具体到手法本身（如"用 generation counter 防定时器竞态"），
   禁止空洞表扬；这部分用于校准，避免审查变成单向挑刺

## 成本红线

- 超过 2000 行的单文件只读相关区段；测试文件仅在评估覆盖质量时抽样
- 报告阶段不再产生探索性工具调用——所有证据必须在阶段 0–3 收齐
- 若用户指定了重点（design/impl/engineering），对应轴全查，其余轴只做
  骨架级快扫并在报告中注明降级范围
